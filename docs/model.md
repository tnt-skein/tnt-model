# Модели данных

`tnt-model` делает объявление формы записи единственным источником:
из него следуют шаг миграции спейса, проверка входа, чтение и запись,
выборка по индексу и фабрика записей для проверок. Одна и та же модель
работает в любой топологии — на одиночном узле, в репликасете,
в шардированном кластере, на узле-прослойке без своих данных — и вне
Tarantool: в таблице PostgreSQL или MySQL через шлюз [`tnt-orm`](https://github.com/tnt-skein/tnt-orm),
который приносит приложение.

```lua
local model = require('tnt.model')

local User = model.define({
    space = 'users',
    fields = {
        { 'id', 'unsigned', primary = true },
        { 'name', 'string', min = 1, max = 255, trim = true },
        { 'age', 'unsigned', min = 0, max = 150 },
    },
    indexes = { age = { parts = { 'age' }, unique = false } },
})

local created, err = User.create({ id = 1, name = 'Мария', age = 46 })
User.where('age', '>=', 18):limit(50):all()
```

Магии — динамических атрибутов, `__index` на каждое обращение,
макросов — нет намеренно: запись — обычная таблица с классом методов,
который видит проверка типов, а функции модели зовутся точкой и
являются обычными замыканиями над формой.

## Зачем пакет

Форма записи без общего места описывается трижды: форматом спейса
в миграции, проверкой входа в домене и полями в службе. Три описания
расходятся молча: поле, добавленное в формат, забывают в проверке,
а ограничение из проверки не попадает в миграцию. Пакет делает четыре
вещи:

- **Одно объявление — четыре следствия.** Из `model.define` выходят
  шаг миграции (`Model.migration()`), схема проверки входа
  (`Model.validate`), доступ по ключу и индексу (`find`, `create`,
  `save`, `delete`, `where`) и фабрика годных записей для проверок
  (`Model.factory`). Расходиться им негде.
- **Где данные, модель не знает.** Шлюз ей привязывает приложение при
  применении конфигурации по ролям узла: `local` — данные здесь,
  `sharded` — через роутер vshard, `remote` — по net.box в репликасет
  с данными, `sql` — таблица в базе через шлюз приложения
  ([`tnt-orm`](https://github.com/tnt-skein/tnt-orm)). Код, который
  зовёт `User.find(7)`, одинаков на роутере, хранилище, реплике,
  прослойке и узле над базой.
- **Отказ — пара `nil, err` с родом.** `invalid` с полями, `conflict`,
  `readonly`, `unavailable`, `misrouted`, `unknown` — обработчик выбирает
  по роду код ответа, а текст отдаёт клиенту как есть. Ошибка
  программиста — неизвестное поле в объявлении, `where` не по индексу,
  обращение к данным до привязки — исключение с текстом, который
  называет модель и место.
- **Большие целые не теряют цифр.** Ключ от 2^53 — снежинка, хеш —
  проходит `create`, `find`, `where` и `after` как cdata `uint64_t`
  или `int64_t`, без приведения к числу Lua, в любой топологии.
- **Привычное — объявлением, а не руками в каждом месте.** Отметки
  «создано» и «изменено», мягкое удаление, хуки вокруг записи
  и именованные условия выборки («только опубликованные») объявляются
  в модели один раз. Отметку и признак удаления ставит узел с данными,
  поэтому их не подделать входом и не потерять заменой ни в одной
  топологии.

Зависимости: `tnt-validate` — проверка входа по форме и раздела
настроек; `tnt-must` — бросок без места вызова и текст отказа
о незнакомой настройке; `tnt-external` — подмена `box`, конфигурации,
vshard, net.box, файбера и часов в проверках; `tnt-clock` — стенные
часы отметок времени. Шаг миграции — функция от `box`, которую
принимает `tnt-schema`; сам пакет `tnt-schema` не берёт. Шлюз к базе
SQL живёт в [`tnt-orm`](https://github.com/tnt-skein/tnt-orm) и приходит
аргументом `model.bind`: от баз SQL пакет моделей не зависит.

## Как пользоваться

### Объявить модель

```lua
-- app/models/user.lua
local model = require('tnt.model')

return model.define({
    space = 'users',
    fields = {
        { 'id', 'unsigned', primary = true },
        model.bucket_of('id'),                              -- ключ шардирования: бакет считается от id
        { 'name', 'string', min = 1, max = 255, trim = true },
        { 'age', 'unsigned', min = 0, max = 150 },
        { 'email', 'string', optional = true },
    },
    indexes = { age = { parts = { 'age' }, unique = false } },
    methods = {
        is_adult = function(self)
            return self.age >= 18
        end,
    },
})
```

| Поле | Что это |
|---|---|
| `space` | имя спейса |
| `fields` | поля **списком**, по порядку кортежа: `{ 'name', 'string', max = 255 }` либо `{ name = 'name', type = 'string' }` |
| `indexes` | `имя = { parts = { поля }, unique = true/false }`; `unique` обязателен, первичный индекс строится из полей с `primary = true`; в шардированном кластере уникальный индекс — только с ключом шардирования среди полей (ниже) |
| `rules` | свои правила: `function(record) return 'текст', 'поле' end` — текст при отказе, второе значение необязательно |
| `methods` | методы записи, зовутся двоеточием: `record:is_adult()`; имена `save`, `delete`, `force_delete`, `restore`, `to_table` заняты |
| `factory` | `function(sequence) return { … } end` — значения фабрики поверх умолчаний по роду |
| `hooks` | хуки записи: `before_create = function(record) … end` и соседи — ниже, «Хуки» |
| `scopes` | области выборки: `published = { { 'published', '=', true } }` — ниже, «Области» |

Поля объявляются списком, а не словарём: порядок полей — это формат
спейса, у словаря Lua порядка нет, а поле, добавленное в словарь,
сдвинуло бы соседей в кортежах, которые уже лежат в базе.

Роды полей: `unsigned`, `integer`, `number`, `string`, `boolean`, `uuid`.
Поля отметок времени объявляют `model.created_at()`, `model.updated_at()`
и `model.deleted_at()` — ниже, «Отметки времени».
Настройки поля: `primary`, `optional`, `default`; у чисел `min`, `max`;
у строк `min`, `max` (в знаках), `pattern`, `one_of`, `trim`. Проверку
делает `tnt-validate`: лишнее поле — отказ, `unsigned` не бывает меньше
нуля, целое не выходит за предел своего рода (ниже, «Большие целые»),
`uuid` принимает опознаватель строкой и cdata, а у записи он строка
(ниже, «Опознаватели»), `trim` обрезает пробелы до проверки. Отказ
проверки — `invalid` с полями: `err.fields.name == 'должно быть строкой
длиной от 1 до 255 знаков, а сейчас 0 знаков'`, текст целиком —
`tostring(err)`.

`trim` режет с краёв только пробельные знаки ASCII — те, что Lua
зовёт `%s`: пробел, табуляции, переводы строки и страницы, возврат
каретки. Неразрывный пробел и прочие пробелы Юникода остаются,
и имя из одного неразрывного пробела проходит `min = 1`:

```lua
User.create({ id = 5, name = ' \tИра\n', age = 30 }).name   -- 'Ира'
select(2, User.create({ id = 6, name = ' \t ', age = 30 })).fields.name
-- 'должно быть строкой длиной от 1 до 255 знаков, а сейчас 0 знаков'
User.create({ id = 7, name = '\u{00A0}', age = 30 }).name    -- '\u{00A0}': неразрывный пробел не обрезан
```

Ошибка в объявлении — ошибка программиста, и падает она при загрузке
модуля модели, а не на первом запросе: «модель users: поле name не знает
настройки mim», «модель users: по полю name индекса нет; есть индексы
primary (id), age (age)».

`model.bucket_of(поле)` — ключ шардирования; поле обязано входить
в первичный ключ. **Он необязателен**: модель без него живёт на узле без
шардирования, а в шардированном кластере привязка откажет с текстом
«нужен model.bucket_of(поле)». Модель с ним на узле без шардирования
поля `bucket_id` не заводит.

`unique = true` держит `box`, а он сверяет значение только со своим
спейсом. В шардированном кластере спейс свой у каждого репликасета,
и уникален по кластеру лишь индекс, среди полей которого есть ключ
шардирования: записи с равными значениями такого индекса — с равным
ключом, то есть в одном бакете и на одном репликасете. Место ключа
в индексе не важно. Уникальный индекс без ключа шардирования держал бы
уникальность только внутри репликасета: тот же `login` у ключей из разных
репликасетов лёг бы дважды молча, и `where('login', '=', …)` отдал бы обе
записи. Поэтому на узле с ролью vshard — роутере, хранилище, узле
«и роутер, и хранилище» — такая модель — исключение `model.bind`:

```lua
local Account = model.define({
    space = 'accounts',
    fields = {
        { 'id', 'unsigned', primary = true },
        model.bucket_of('id'),
        { 'login', 'string' },
    },
    indexes = { login = { parts = { 'login' }, unique = true } },
})

model.bind({ Account }, settings)
-- исключение: модель accounts: уникальность индекса login в шардированном кластере
-- не гарантирована — среди его полей нет ключа шардирования id
```

Логин, уникальный в пределах арендатора, — индекс
`{ parts = { 'login', 'tenant' }, unique = true }` при ключе шардирования
`tenant`, и такой привязка пропускает. Без vshard данные в одном
репликасете, у источника `sql` — в базе, уникальность там держится
целиком, и сверки нет; модель без ключа шардирования на хранилище
не шардирована — у каждого репликасета свои её записи, — и её тоже
не сверяют.

### Поднять схему

`Model.migration()` — функция от `box`: спейс с форматом по объявлению,
первичный индекс, индексы модели. Это шаг для `tnt-schema` — или для
чего угодно, что зовёт функцию с `box` под транзакцией:

```lua
local schema = require('tnt.schema')

schema.register(1, User.migration())
```

Шаг выполняется один раз: он создаёт спейс, и повторный вызов на узле,
где спейс уже есть, — исключение `box` «Space 'users' already exists».
Версия `tnt-schema` зовёт шаг ровно однажды. Сценарий, который поднимает
схему сам при каждом применении конфигурации, проверяет, что спейса
ещё нет, — иначе он упадёт на втором старте узла:

```lua
if box.space.users == nil then
    box.atomic(User.migration(), box)
end
```

Подробности — ниже, в «Миграция».

### Привязать к узлу

До привязки модель данных не видит: `User.find(7)` — исключение
«модель users не привязана: узел ещё не применил конфигурацию».
Привязку делает приложение при применении конфигурации — в роли, в
сценарии узла, — и порядок тот же везде:

```lua
local model = require('tnt.model')

local settings = model.settings(section)         -- раздел `models` настроек, проверенный; nil — умолчания
local binding = model.bind({ User, Order }, settings)   -- шлюз по ролям узла; противоречие — исключение
-- источник sql: шлюз к базе приносит вызывающий — model.bind(модели, settings, { sql = orm.gateway(db) })

binding.attach()                                  -- модели переключаются на шлюз

for name, fn in pairs(binding.functions) do      -- на узле с данными — функции tnt_model_*
    rawset(_G, name, fn)
end

binding.status()   -- { source = 'local', sharded = false, serves = true, spaces = { 'users', 'orders' } }
```

`model.bind` собирает привязку целиком, ничего ещё не переключая:
заводит шлюз, сверяет топологию с моделями, готовит функции узла
с данными. Только `attach` переключает модели, поэтому сорвавшаяся
сборка ничего не меняет: узел отвечает прежней привязкой. При
перечитывании конфигурации новая привязка собирается рядом, `attach`
переключает модели на неё, и только потом `close` отпускает прежнюю —
модель, уже переключённая на новую, при ней и остаётся. Вызов, начатый
на прежней привязке, доходит до ответа: её соединения шлюз `remote`
закрывает, когда вызовов в пути не останется (ниже, «Шлюз `remote`»).
Запись, которую ведущий принял в миг перечитывания, вызывающий получает
записью, а не отказом.
`close` последней привязки отвязывает модели, и обращение к данным
снова становится ошибкой программиста. Текст называет причину: узел
конфигурацию применил и отпустил, и «ещё не применил» уводило бы искать
поломку применения:

```lua
binding.close()

User.find(7)                  -- исключение: модель users не привязана: привязка закрыта, новой нет
model.atomic(function() end)  -- исключение: model.atomic: у узла нет привязанных моделей — привязка закрыта, новой нет
```

Функции `tnt_model_*`, опубликованные глобалами, `close` не трогает:
у них свой шлюз `local`, собранный вместе с привязкой, и после `close`
они читают и пишут дальше — роутер и прослойка по-прежнему пишут
в спейс узла. Снимает их тот, кто публиковал, — при остановке роли,
вместе с `close`. При перечитывании функции новой привязки встают
на те же имена, а у узла, который данных больше не держит
(`binding.functions` новой привязки пуст), прежние снимаются так же.

```lua
-- остановка роли
for name in pairs(binding.functions) do
    rawset(_G, name, nil)
end

binding.close()
```

Привязка одна на процесс: `model.atomic` спрашивает у неё шлюз, а
`attach` следующей переключает его на себя.

### Читать и писать

```lua
local record, err = User.validate(input)          -- запись по форме, в хранилище не пишет
local created, err = User.create(input)           -- проверка и вставка; занятый ключ либо уникальный индекс — conflict
local found = User.find(7)                         -- запись либо nil; nil, err — отказ узла
found.age = 47
found:save()                                       -- проверка и замена по ключу
found:delete()                                     -- по ключу записи
User.delete(7)                                     -- true — была, false — не было
User.force_delete(7)                               -- окончательно; у модели без deleted_at — как delete

User.where('age', '>=', 18):limit(50):all()        -- страница по индексу
User.where('age', 'between', { 30, 40 }):count()
User.where('age', '<', 18):first()
User.where('age', '>=', 18):limit(50):after(page[#page]):all()   -- следующая страница
User.where('age', '>=', 18):limit(50):offset(100):all()          -- третья страница по номеру
User.scan():limit(100):all()                       -- полный обход — только явно и страницами

User.factory({ name = 'Мария' })                   -- годная запись для проверок; :save() кладёт
```

Отказ — пара `nil, err`; исключение — ошибка программиста: незнакомое
поле в объявлении, `where` не по индексу (текст называет индексы, по
которым искать можно), обращение к данным до привязки («узел ещё не
применил конфигурацию») и после `close` («привязка закрыта, новой
нет»). Отметки времени, хуки, мягкое удаление и области — ниже, в своих
разделах.

### Большие целые

Целые от 10^14 по модулю `box` и net.box отдают cdata `uint64_t` либо
`int64_t`, `json.decode` — от 2^53, причём положительные до 2^63 —
`int64_t`. Роды `unsigned`, `integer` и `number` принимают такое значение
как есть, с проверкой `min` и `max`, и к числу Lua не приводят: число
держит целые подряд только до 2^53, и `2^53 + 1` в нём уже `2^53`. Так
ключ вроде снежинки проходит `create`, `find`, `save`, `where` и `after`
в любой топологии:

```lua
local input = json.decode('{"id": 9007199254740993, "name": "Мария", "age": 46}')

tostring(input.id)                         -- '9007199254740993LL': так отдаёт JSON
tostring(User.create(input).id)            -- '9007199254740993ULL': так отдаёт box
User.find(9007199254740993ULL).name        -- 'Мария'; User.find(2 ^ 53) — nil, это другой ключ
User.where('id', '>', 2 ^ 53):first().name -- 'Мария'
User.create({ id = 18446744073709551615ULL, name = 'Иван', age = 30 }).id == 18446744073709551615ULL  -- true
json.encode({ id = User.find(9007199254740993ULL).id })  -- '{"id":9007199254740993}'
select(2, User.find(-1LL)).fields.id       -- 'должно быть целым числом не меньше 0, а не -1'
```

Отказ называет значение цифрами, без `ULL`: текст тот же, что у числа
Lua за той же границей. Порядок страницы, слитой с нескольких хранилищ,
и граница `between` сравнивают такие значения точно — `<` LuaJIT этого
не умеет: он приводит обе стороны к `uint64_t`, стоит одной быть им,
и `-1` выходит больше `5ULL` и равным `2^64 − 1`.

Число Lua за пределом рода `box` в целое поле не кладёт: `unsigned`
держит его в `[0, 2^64)`, `integer` — в `[-2^63, 2^64)`, а дальше видит
в нём `double` и бросает исключение. Такое число приходит снаружи —
`json.decode('{"id": 1e20}')` отдаёт его числом, — поэтому модель
отвечает на него отказом `invalid` в записи, ключе, условии и курсоре
ещё до `box`, а через роутер — не ходя на хранилище: без этого клиент
получал бы исключение на узле с данными и `unavailable` через роутер,
503 вместо 422. Предел рода отказ называет, только когда его перешли:
у обычного промаха текст прежний, и объявленный `max` важнее предела
рода. Предел объявления шире рода (`max = 1e30`) ничего не сужает
и снимается. У `number` предела рода нет — он держит `double` любой
величины:

```lua
select(2, User.create(json.decode('{"id": 1e20, "name": "Мария", "age": 46}'))).fields.id
-- 'должно быть целым числом от 0 до 18446744073709551615, а не 1e+20'
select(2, User.find(2 ^ 64)).kind                           -- 'invalid', а не исключение box
select(2, User.where('id', '>=', 1e20):all()).kind          -- 'invalid'
tostring(User.create({ id = 2 ^ 64 - 2048, name = 'Край', age = 30 }).id)
-- '18446744073709549568ULL': наибольший double меньше 2^64 box кладёт целым
```

Не-число (NaN) модель записать не даст — его отвергает проверка входа, —
но в поле `number`, записанном мимо модели, оно лежит, и индекс TREE
ставит его раньше любого числа, даже `-inf`. Туда же его ставят слитая
страница и условия областей — и против числа Lua, и против целого cdata:
порядок не зависит ни от того, каким родом пришло целое, ни от машины.

### Опознаватели

Поле `uuid` принимает опознаватель строкой в любом регистре и cdata
`uuid` — его отдают `uuid.new()`, `uuid.fromstr` и кортеж чужого спейса.
У записи он один видом — строка в нижнем регистре: такой его отдают
`create`, `find`, `save`, выборки и функции узла с данными, такой он
уходит в JSON и по проводу. Требовать от вызывающего `tostring`
значило бы переложить на него то, как устроен `box`, а два вида
у записи — сравнивать их в каждом обработчике. Ключ `find` и `delete`,
значение и границы `where`, курсор `after` и значения областей тоже
берут оба вида:

```lua
local uuid = require('uuid')

local Device = model.define({
    space = 'devices',
    fields = {
        { 'id', 'uuid', primary = true },
        { 'owner', 'uuid' },
        { 'serial', 'uuid', default = uuid.new },   -- умолчание-функция: у записи строка
    },
    indexes = { owner = { parts = { 'owner' }, unique = false } },
})

local id = '6ba7b810-9dad-41d1-80b4-00c04fd430c8'
local owner = uuid.new()
local created = Device.create({ id = id:upper(), owner = owner })

created.id                                            -- '6ba7b810-9dad-41d1-80b4-00c04fd430c8'
type(created.owner), type(created.serial)             -- 'string', 'string'
Device.find(uuid.fromstr(id)).id == Device.find(id).id   -- true: ключ — строкой либо cdata
Device.where('owner', '=', owner):count()             -- 1; строкой — так же
json.encode({ id = created.id })                      -- '{"id":"6ba7b810-9dad-41d1-80b4-00c04fd430c8"}'
uuid.is_uuid(box.space.devices:get(uuid.fromstr(id)).id)   -- true: в спейсе — cdata
select(2, Device.find('нет')).fields.id               -- "должно быть UUID, а не 'нет'"
Device.delete(uuid.fromstr(id))                       -- true
```

В `box` поле `uuid` держит cdata и строки не примет ни в кортеже,
ни в ключе, ни в курсоре `after` — «expected uuid, got string»
и исключение вместо отказа (сверено на 3.8). Поэтому опознаватель
переводит шлюз `local` — только там, где зовёт `box`: запись из спейса
приходит строкой, а в кортеж, ключ и курсор уходит cdata. Через роутер
и прослойку он едет строкой, а переводит его тот же шлюз на узле
с данными.

Умолчание поля — значение либо функция вроде `uuid.new` — становится
строкой так же: умолчание минует проверку `tnt-validate`, и без этого
запись из `validate` и хук «до» видели бы cdata. Негодное умолчание
остаётся как есть, и `box` отвергает его исключением: это ошибка
объявления.

Порядок строк тот же, что у опознавателей в индексе: строки одной длины
из шестнадцатеричных цифр в нижнем регистре сравниваются поле за полем,
как `box` сравнивает сами опознаватели (сверено на 3.8). Поэтому
страница, слитая роутером с нескольких хранилищ, граница `between`
и условия областей сравнивают строки, и продолжение `after` не теряет
и не повторяет записей.

Бакет ключа шардирования `uuid` роутер и хранилище считают от строки
в нижнем регистре. Номер от cdata и от строки другого регистра другой,
поэтому бакет функции узла с данными (ниже, «Транзакции») берут
от значения записи: `vshard.router.bucket_id_mpcrc32(device.id)`.

### Запись

Запись — таблица по именам полей с метатаблицей класса. `save()` после
успеха оставляет в записи то, что легло в хранилище: умолчания
заполнены, пробелы обрезаны. `to_table()` — копия без метатаблицы.
Поле шардирования в записи не показывается, в кортеж кладётся.

### Фабрика

`Model.factory(поля)` собирает годную запись из порядкового номера
вызова: поверх умолчаний по роду — `factory` из объявления, поверх неё —
аргумент. Необязательные поля фабрика не заполняет. Умолчания по роду:
логическое — `false`, `uuid` — новый, число — номер, прижатый
к `min`/`max`, строка — первое из `one_of` либо «имя номер»
(`'name 1'`), дописанная знаком `x` до `min`. Строка длиннее `max`
теряет начало, а не конец: номер стоит в конце, и у двух записей
с полем `{ 'code', 'string', max = 3 }` значения разные — `'e 1'`
и `'e 2'`, — а не одна голова `'cod'`, на которой столкнулись бы ключи.
Поле с `max` меньше единицы получает пустую строку. Запись, не прошедшая
проверку модели, — ошибка программиста: «фабрика модели users собрала
негодную запись: …».

### Выборка

Только по индексу: `where(поле, знак, значение)`, где поле — первое звено
какого-то индекса, знаки `=`, `>`, `>=`, `<`, `<=` и `between` с парой
`{ от, до }` (обе границы включительно). `<` и `<=` идут по убыванию.
Страница — `limit(n)`, без него `model.LIMIT` (100): поле называет
страницу, а не задаёт её, и его правка выборку не меняет. Размер
страницы — целое от 1 до `model.OFFSET` (2^32 − 1), по той же причине,
что у смещения ниже: `limit(2^32 + 5)` `box` молча обрезал бы до пяти
записей, поэтому иное — исключение «модель users: limit — целое число
от 1 до 4294967295, а не 0». Продолжение —
`after(запись)`: из записи берутся части индекса и первичный ключ, так
страница не зависит от вставок между запросами и одинаково считается
на одном узле и слиянием с нескольких хранилищ. `count()` считает
без страницы и смещения. Диапазон `between` считается двумя счётами
по индексу — записи от нижней границы без записей строго за верхней:
счёт не читает записей и не уступает, миллион записей считается
за 0,1 мс, одинаково в транзакции и вне её и одним снимком. Верхняя
граница ниже нижней — пустой диапазон, ноль. `first()` — `limit(1)`.

Страница по номеру — смещение: `offset(n)` пропускает n записей от начала
выборки, `offset((номер - 1) * размер)`. Граница `between` режет страницу
после пропуска, со смещением `after` складывается: `after(запись):offset(n)`
пропускает n записей после курсора. Смещение — целое от 0 до
`model.OFFSET` (2^32 − 1): `box` держит его в 32 битах и большее молча
обрезает — смещение 2^32 отдало бы первую страницу, поэтому иное —
исключение «модель users: offset — целое число от 0 до 4294967295,
а не -1». Страница за концом пуста:

```lua
User.where('age', '>=', 18):limit(3):offset(0):all()   -- записи 1–3 по возрасту
User.where('age', '>=', 18):limit(3):offset(3):all()   -- 4–6
User.where('age', '>=', 18):limit(3):offset(300):all() -- {} — за концом
```

На узле с данными смещение дёшево: индекс TREE memtx на Tarantool 3.8
пропускает записи, не читая их, — 999 990 записей за 33 мкс. Через
роутер vshard оно стоит дорого — ниже, «Смещение через роутер».

Значение условия проверяется по тому, чем оно служит. **Искомое
значение** равенства (`=`) — всем правилом поля: пределами, длиной,
образцом, перечнем. Записи с негодным значением быть не может, и такой
запрос — ошибка клиента: `where('age', '=', 200)` при `max = 150` —
отказ. **Граница** диапазона (`<`, `<=`, `>`, `>=`, `between`) и курсор
`after` — только родом поля: это место в порядке индекса, а не значение
записи. Поэтому `where('age', '<', 200)` обходит весь индекс по убыванию,
`where('login', '>=', '')` у поля `login` с `min = 1` — весь по
возрастанию, а страница продолжается и после записи, лёгшей до того, как
объявление сузили. Род у границы остаётся: строка в числовом поле, дробь
в целом, число за пределом рода — отказ, и `-1` в беззнаковом тоже:
такого ключа `box` в индекс `unsigned` не примет, начало беззнакового
индекса — `>= 0`.

```lua
#User.where('age', '<', 200):all()                         -- все записи, по убыванию возраста
User.where('age', 'between', { 0, 200 }):count()           -- все записи
select(2, User.where('age', '=', 200):all()).fields.age   -- 'должно быть целым числом от 0 до 150, а не 200'
select(2, User.where('age', '>=', 'x'):all()).fields.age  -- "должно быть целым числом не меньше 0, а не 'x'"
select(2, User.where('age', '>=', -1):all()).fields.age   -- 'должно быть целым числом не меньше 0, а не -1'
tostring(select(2, User.where('age', '=', 200):all()))
-- 'условие выборки users: age — должно быть целым числом от 0 до 150, а не 200'
```

Негодное значение — отказ `invalid` из `all()`/`first()`/`count()`,
а не исключение: значение пришло снаружи. Текст отказа начинается
с «условие выборки users:», а не с «запись users не прошла проверку»:
негодна не запись, а то, чем её ищут. Пустое значение — тоже отказ,
а не полный обход: `where('age', '>=', nil)` отвечает `err.fields.age ==
'обязательное поле'`. Условие ищут, а не заполняют, поэтому умолчание
и необязательность поля к нему не применяются.

Курсор `after` приходит от клиента так же, как граница условия, и его
части индекса и ключа проверяются родом полей. Негодное значение — тоже
отказ `invalid` из `all()`/`first()`/`count()`, а не исключение и не
`unavailable`: без проверки `box` отвечал бы на него «Iterator position
is invalid», и через роутер ошибка клиента читалась бы бедой хранилища.
Отказ называет первое негодное поле — части индекса раньше ключа.
Пустота обязательного поля из JSON (`null`) — отказ «обязательное поле»,
а обязательного поля нет вовсе — исключение «модель users: в after нет
поля id»: у записи страницы оно есть всегда, и такой курсор собрал код.
Пустота необязательного поля — ни то ни другое: это место NULL
в индексе (ниже).

```lua
local _, err = User.where('age', '>=', 18):after({ age = 'x', id = 1 }):all()

err.kind         -- 'invalid'
err.fields.age   -- "должно быть целым числом не меньше 0, а не 'x'"
select(2, User.scan():after(json.decode('{"id": null}')):first()).fields.id  -- 'обязательное поле'
User.where('age', '>=', 100):after({ age = 151, id = 1 }):all()           -- {}: 151 за max, но место в индексе
```

Курсор приходит и от другой выборки: клиент продолжает страницу
записью, которой в этой выборке нет. Страница после курсора — записи
выборки строго после него в порядке обхода, откуда бы он ни пришёл:
курсор раньше начала выборки отдаёт её целиком, курсор за концом —
пустую страницу. Так отвечает любая топология, и шлюз `sql` тоже.
Сам `box` на такой курсор страницей не отвечает: раньше начала он его
отвергает — «Iterator position is invalid», на узле с данными
исключением, через роутер отказом `unavailable`, хотя ошибся клиент, —
у `=` отвергает и курсор за концом, а у `>` и `<` курсор со значением
самого ключа принимает и отдаёт записи с этим значением, которых
в выборке нет. Поэтому шлюз `local` сверяет курсор с ключом выборки
до `box`, по частям ключа и порядку обхода: раньше начала курсор
не передаётся вовсе, за концом равенства страница пуста без обращения
к индексу. Курсор за концом диапазона `box` принимает и сам отдаёт
пустую страницу. Смещение с курсором раньше начала отсчитывается
от начала выборки.

```lua
-- возраст: у записей 1, 2 и 5 — 100, у 3 — 120, у 4 — 5, у 6 — 149
User.where('age', '>=', 100):after({ age = 5, id = 1 }):all()     -- 1, 2, 5, 3, 6: вся выборка
User.where('age', '>', 100):after({ age = 100, id = 1 }):all()    -- 3, 6: возраста 100 в ней нет
User.where('age', '<=', 100):after({ age = 120, id = 1 }):all()   -- 5, 2, 1, 4: по убыванию раньше — больше
User.where('age', '=', 100):after({ age = 120, id = 1 }):all()    -- {}: за концом равенства
User.where('age', '>=', 100):after({ age = 149, id = 1 }):all()   -- 6: курсор в выборке
```

Индекс по необязательному полю допустим. Пустое значение в нём идёт
первым, как NULL в индексе TREE: с индексом по `email` выборка
`where('email', '<', 'n')` отдаёт записи без почты в конце. Этот порядок
одинаков на одном узле, в странице, слитой с нескольких хранилищ,
и в таблице шлюза `sql`.

Страница, кончившаяся записью без почты, продолжается от её места.
Пустая часть необязательного поля в курсоре — поля нет у записи либо
`null` пришёл из JSON — это NULL в индексе, а не нехватка поля и не
отказ; непустая проверяется родом, как всякая часть курсора. Поэтому
страницы по убыванию проходят записи без почты до конца, а в составном
индексе, где такое поле не первое, — и по возрастанию, где записи
без него идут первыми. Выборка `>=` по индексу почты записей без
почты не берёт, и курсор с пустой почтой стоит раньше её начала:
страница после него — вся выборка (выше). Курсор с пустой почтой едет
хранилищам и прослойке по проводу, и обход страницами отдаёт каждую
запись ровно по разу на любой топологии и у шлюза `sql`:

```lua
-- User с indexes = { email = { parts = { 'email' }, unique = false } }:
-- 1 — 'c@x', 2 — без почты, 3 — 'a@x', 4 — без почты, 5 — 'b@x'
local first = User.where('email', '<', 'z'):limit(2):all()                   -- 1, 5
local second = User.where('email', '<', 'z'):limit(2):after(first[2]):all()   -- 3, 4
User.where('email', '<', 'z'):limit(2):after(second[2]):all()                 -- 2: после записи 4 без почты
User.where('email', '<=', 'z'):after(json.decode('{"email": null, "id": 4}')):all()  -- 2
User.where('email', '>=', 'a'):after({ id = 4 }):all()                        -- 3, 5, 1: вся выборка
select(2, User.where('email', '<', 'z'):after({ email = 5, id = 4 }):all()).fields.email
-- 'должно быть строкой, а не 5'
```

### Отметки времени

```lua
local Post = model.define({
    space = 'posts',
    fields = {
        { 'id', 'unsigned', primary = true },
        { 'title', 'string', min = 1, max = 200 },
        { 'published', 'boolean', default = false },
        { 'locked', 'boolean', default = false },
        model.created_at(),     -- поставлена при создании
        model.updated_at(),     -- ставится при каждой записи
        model.deleted_at(),     -- признак мягкого удаления, ниже
    },
    indexes = { created = { parts = { 'created_at' }, unique = false } },
})

local post = Post.create({ id = 1, title = 'Первая' })
post.created_at, post.updated_at        -- 1790000000.25, 1790000000.25 — секунды от начала эпохи
post.title = 'Первая, правка'
post:save()
post.created_at, post.updated_at        -- 1790000000.25, 1790000042.5
```

Поле отметки — необязательное число секунд от начала эпохи по стенным
часам `tnt-clock` (`clock.realtime`): отметка переживает перезапуск
и уезжает на другие узлы, а монотонные часы чужого процесса со своими
несравнимы. Место поля в списке — место в кортеже, как у всякого поля:
отметки, дописанные в конец неявно, сдвинули бы поля, добавленные
после них. Имя меняется аргументом — `model.created_at('made_at')`.
Индекс по отметке объявляется как по любому полю, и `where('created_at',
'>=', t)` идёт по нему.

Отметку ставит узел с данными — шлюз `local`, — а не тот, кто зовёт
модель, и из входа она не берётся никогда:

- вставка — отметки создания и изменения равны часу записи, признака
  удаления нет;
- замена (`save`) — отметка изменения — час записи, а отметка создания
  и признак удаления переходят от прежней записи с тем же ключом,
  тем же обращением к спейсу, без уступки между чтением и записью.
  Прежней записи нет — как при вставке;
- мягкое удаление и восстановление ставят и снимают признак и тоже
  двигают отметку изменения.

Так отметка создания не теряется, даже если запись сохранили, не читая
(`User.validate(input):save()`), или сохраняли через роутер, пока
реплика, с которой её читали, отставала: прежнюю запись смотрит тот
узел, который пишет. Запись, лёгшая до появления отметок, так и
остаётся с пустой отметкой создания: час её создания неизвестен.

Через роутер vshard и прослойку отметку ставит хранилище: функция
узла с данными `tnt_model_put` пишет шлюзом `local`. Поэтому и запись,
пришедшая по `lua_call` мимо модели вызывающего, получает отметки.

### Хуки

```lua
local Post = model.define({
    space = 'posts',
    fields = { … },
    hooks = {
        before_update = function(post, original)
            if original.locked then
                return nil, 'запись заперта — менять её нельзя'
            end
        end,
        before_create = function(post)
            post.title = post.title:gsub('%s+', ' ')   -- поправленное проверяется ещё раз
        end,
        after_delete = function(post)
            log.info('удалена запись %d', post.id)
        end,
    },
})

local post = Post.find(1)         -- запись с locked = true
post.locked = false
post:save()                        -- nil, err: err.kind == 'refused', tostring(err) == 'запись заперта — менять её нельзя'
```

Хуки — `before_*` и `after_*` четырёх событий:

| Событие | Когда | Аргументы хука |
|---|---|---|
| `create` | `create`, `save` записи, которую не читали из хранилища (`validate`, `factory`) | запись |
| `update` | `save` записи, прочитанной из хранилища (`find`, выборка, `create`, прошлый `save`) | запись и `original` — та же запись, какой её прочитали |
| `delete` | `delete` и `force_delete`, по ключу и у записи | запись |
| `restore` | `restore`, по ключу и у записи | запись |

Хук «до» отказывает, как всякая функция набора, — парой: `return nil,
'причина'` даёт отказ рода `refused` с этим текстом, `return nil, отказ`
передаёт отказ модели как есть (хук, который сам зовёт модель, отдаёт
её `unavailable` без перевода), голое `return false` — отказ «хук
before_update модели posts отказал в записи». Отказ отменяет запись:
до шлюза она не доходит, вызывающий получает отказ парой. Пусто
и истина — запись идёт дальше.

Хук «до» создания и изменения получает запись уже после проверки
и вправе её поправить: поправленное проверяется ещё раз, и в спейс
ложится только то, что прошло форму. Хук «до» удаления получает запись
из рук: у `record:delete()` — саму запись, у `Post.delete(7)` —
прочитанную по ключу. Удаление по ключу у модели с хуками удаления
читает запись: хуку нужна запись, а не ключ; не нашлась — `false`,
и хук не зовётся. Без хуков события ключ уходит шлюзу сразу, одним
обращением. Хук «до» зовётся на попытку: удаление уже удалённой записи
и восстановление живой его зовут, а шлюз отвечает `false`.

Хук «после» идёт, когда запись легла, и получает её такой, какой она
легла, — с отметками и умолчаниями. Его ответ ничего не отменяет:
отменить легшую запись вне транзакции нечем. Внутри `model.atomic`
исключение хука откатывает транзакцию целиком — и запись вместе с ней.

Хуки идут там, где зовут модель, — на роутере, прослойке, узле
с данными, — и ровно один раз: функции `tnt_model_*` узла с данными
хуков не зовут. Иначе запись через роутер прошла бы их дважды, а хук,
который сам пишет через модель, на хранилище писал бы мимо роутера.

`original` — запись, какой её прочитал этот процесс, а не свежая
из хранилища: хук, которому важно нынешнее состояние, читает сам —
на узле с данными в `model.atomic`, где чтение и запись одна транзакция.

### Мягкое удаление

```lua
Post.delete(1)                                 -- true: у записи появился deleted_at
Post.find(1)                                   -- nil: поиск по ключу удалённую не видит
Post.scan():all()                              -- без записи 1
Post.scan():count()                            -- без записи 1
Post.where('id', '=', 1):with_deleted():first().deleted_at   -- 1790000100.5
Post.scan():only_deleted():all()               -- только удалённые
Post.restore(1)                                -- true: отметка снята, запись видна снова
Post.force_delete(1)                           -- true: записи в спейсе больше нет
```

Поле `model.deleted_at()` делает удаление мягким: `delete` — по ключу
и у записи — ставит отметку удаления, а не стирает запись. Удалённую
не видят `find` и выборка: `all`, `first`, `count`. `with_deleted()`
показывает её вместе с живыми, `only_deleted()` — только удалённые.
`restore` снимает отметку, `force_delete` стирает запись из спейса.
Ответ — `true`, если было что менять, и `false`, если нет: удалённую
не удаляют второй раз, живую не восстанавливают. Запись в руках после
`record:delete()` и `record:restore()` заполняется тем, что легло,
вместе с отметкой.

`save` признак удаления не меняет: он переходит от прежней записи,
и удалённая запись, сохранённая заново, остаётся удалённой. `create`
с ключом удалённой записи — `conflict`: запись в спейсе есть.

`force_delete` есть у всякой модели — у модели без мягкого удаления
это то же, что `delete`. `restore`, `with_deleted` и `only_deleted`
у модели без `model.deleted_at()` — ошибка программиста: «модель users:
restore — только у модели с мягким удалением, model.deleted_at()».

### Области

```lua
local Post = model.define({
    space = 'posts',
    fields = { … },
    scopes = {
        published = { { 'published', '=', true } },
        since = function(moment)
            return { { 'created_at', '>=', moment } }
        end,
    },
})

Post.scan():scope('published'):limit(20):all()
Post.where('created_at', '>=', t):scope('published'):count()
Post.scan():scope('published'):scope('since', t):with_deleted():all()
```

Область — именованный список условий `{ поле, знак, значение }`,
которые добавляются к выборке: `:scope(имя)` сужает её, области
складываются друг с другом и с условием мягкого удаления. Знаки — `=`,
`~=`, `<`, `<=`, `>`, `>=`. Пустое значение при `=` значит «значения
нет», при `~=` — «значение есть»: `{ 'email', '=', nil }`. Сравнение —
в порядке индекса TREE: пустое значение меньше любого, и `{ 'age', '<',
18 }` берёт записи без возраста, как `where('age', '<', 18)`.

Значение условия проверяется тем же правилом, что у `where`: при `=`
и `~=` — всем правилом поля, при `<`, `<=`, `>`, `>=` — только родом,
это граница. `{ 'age', '<', 200 }` годится при `max = 150`, `{ 'age',
'=', 200 }` — нет: записи с таким значением быть не может, и условие
с ним — ошибка.

Область-функция принимает аргументы и отдаёт условия: `scope('since',
t)`. Её аргумент приходит снаружи, и негодное значение — отказ
`invalid` из `all()`, `first()` и `count()`, как негодное значение
`where`: `err.fields.created_at`, текст — «условие выборки posts: …». Область-список проверяется при
объявлении, и её ошибка падает при загрузке модуля модели: «модель
posts: область published: published — должно быть логическим
значением, а не 'да'». Незнакомая область и аргументы у области-списка —
ошибка программиста.

Область — не индекс. Выборка идёт по индексу `where` либо обходом
`scan`, а условия проверяет узел с данными у каждой записи: условие
— данные, а не функция, и через роутер и прослойку оно едет по проводу
вместе с выборкой. Индекс по полю области объявляют, когда по нему
ищут часто, — и ищут тогда `where` по нему.

Выборку с условием `box` сам не выполнит: узел с данными берёт записи
индекса кусками по тысяче, с уступкой между кусками вне транзакции,
и отбирает подходящие. Выборка короче куска идёт одним куском, без
уступки и одним снимком. Страница, смещение и `after` считают
только подошедшие записи; страница кончается, как только набралась.
Цена — в «Чем пришлось поступиться».

### Отказы

`err.kind`: `invalid` (запись либо условие выборки не прошли проверку,
с `fields`), `conflict` (`create` на занятый ключ, `create` и `save`
со значением уникального индекса, которое уже у другой записи; текст
называет индекс — «запись accounts с таким login уже есть», первичный
зовёт ключом — «запись users с таким ключом уже есть»),
`readonly` (узел или репликасет только для чтения), `unavailable`
(хранилище не ответило, схема не поднята, спейс снесли посреди
выборки с условием, бакет в переносе посреди
транзакции узла «и роутер, и хранилище», веер не получил ссылку
на хранилище за срок, пока переезжают бакеты), `misrouted` (запись мимо
роутера в чужой бакет), `unknown` (спейс не в белом списке узла),
`refused` (хук «до» отказал в записи).
`model.failure.is(err)`, `tostring(err)`, `err .. ''` и `json.encode`
дают текст.

Текст `readonly` узла с данными — «узел только для чтения: config»,
и после двоеточия стоит `box.info.ro_reason` узла как есть: причину
называет Tarantool, а не пакет. У реплики с назначенным ведущим это
`config`, у последователя при `failover: election` — `synchro`
(сверено на 3.8); `election` и `orphan` Tarantool ставит в своих
случаях. Примеры в разделах ниже показывают `config`, а на последователе
с выборами тот же отказ выглядит так:

```lua
-- на последователе репликасета с failover: election
box.info.ro_reason                                       -- 'synchro'
tostring(select(2, User.create({ id = 9, name = 'Вера', age = 33 })))
-- 'узел только для чтения: synchro'
```

и узел без данных по ролям неотличимы, поэтому прослойка объявляет себя
сама; базу по ролям узла не угадать вовсе. Узел «и роутер, и хранилище»
получает `sharded` и ходит через свой роутер даже к своим бакетам, но
в транзакции идёт к ним на месте (ниже, «Транзакции»).

### Раздел `models`

Раздел — таблица настроек, которую приложение отдаёт `model.settings`;
имя раздела — `model.SECTION` (`models`). Откуда приложение его берёт —
его дело: из `roles_cfg` своей роли, из меток узла, из файла. Стенд
проверок пакета собирает его из меток `model_source`,
`model_replicaset`, `model_writes`; роль приложения читала бы его так:

```yaml
groups:
  gateways:
    roles: [app]
    roles_cfg:
      app:
        models: { source: remote, replicaset: core, timeout: 5 }
```

Настройки: `source` — `auto` (по правилу), `local`, `sharded`, `remote`,
`sql`; `replicaset` — где данные (для `remote`); `timeout` — срок
обращения к чужому узлу, секунды, по умолчанию 5: у шлюза `remote` —
к одному узлу репликасета, соединение и вызов вместе (ниже, «Шлюз
`remote`»), у шлюза `sharded` — вызова через роутер, у веера — вместе
с повтором (ниже, «Шлюз `sharded`»); `writes` — что реплика без
шардирования делает с записью: `local` (по умолчанию) — отказ
`readonly`, `forward` — пересылка ведущему (ниже, «Пересылка записи
с реплики»); `driver` — имя драйвера
SQL для `sql`, по умолчанию `db`: по нему приложение берёт драйвер
из своего контейнера (ниже, «Шлюз `sql`»).
Негодное значение — исключение `model.settings` с текстом `tnt-validate`:
«раздел models: срок должен быть числом не меньше 0.001, а не 0»,
«раздел models: неизвестная настройка peers». Противоречие раздела
с ролями узла — исключение `model.bind` с понятным текстом: «источник
sharded: у узла нет роли router vshard», «источник remote: репликасет
core — свой, данные были бы на месте», «пересылка записи: у узла с ролью
vshard запись ходит через роутер», «пересылка записи: у источника sql
данные в базе — запись и так уходит туда», «источник sql: шлюза нет —
его приносит тот, кто собирает привязку: model.bind(модели, раздел,
{ sql = orm.gateway(db) })»; узел при этом остаётся при прежней
привязке. Схему на прослойке поднимать не нужно: данных у неё нет, —
а без `source: remote` прослойка получила бы шлюз `local` и пустые
спейсы у себя.

### Общие функции узла с данными

На узле, который держит данные, привязка отдаёт в `binding.functions`
пять функций — `tnt_model_find(space, key)`, `tnt_model_put(space,
values, mode)`, `tnt_model_delete(space, key, mode)`,
`tnt_model_select(space, query)`, `tnt_model_count(space, query)` —
**по белому списку моделей приложения**: чужой спейс по имени отвечает
`unknown`. Приложение
публикует их глобалами, и роутер с прослойкой зовут их по iproto. Вход
проверяется на узле заново: роутер проверил его у себя, но узел
с данными не верит тому, кто зовёт функцию. Проверка стоит только
на пути через функции: учётка с правом записи в спейс пишет в него
и мимо них (ниже, «Права»). Ответ — одна таблица
`{ ok = true, value = … }` либо отказ `{ ok = false, kind, message,
fields }`: vshard отдаёт вызывающему только первое значение.

Ключ и запись проверяются правилами модели, значения выборки — теми
же правилами, что у `where`, `after`, областей, `limit` и `offset`:
части ключа у итератора `EQ` — всем правилом поля, у остальных —
родом, как граница (`ALL` с ключом `box` ведёт от ключа, как `GE`);
частей не больше, чем у индекса; граница `to`, курсор `after`
и значения условий `filter` — как у модели; `limit` — целое от 1
до `model.OFFSET`, `offset` — от 0. Правило одно: выборку, которую
модель собрала на роутере, хранилище примет, а негодная — отказ
`invalid` с полями, а не исключение `box` и не весь спейс при
`limit = -1`:

```lua
tnt_model_select('users', { index = 'primary', iterator = 'ALL', key = {}, limit = -1 })
-- { ok = false, kind = 'invalid', fields = { limit = 'должно быть целым числом от 1 до 4294967295, а не -1' },
--   message = 'условие выборки users: limit — должно быть целым числом от 1 до 4294967295, а не -1' }
tnt_model_count('users', { index = 'age', iterator = 'GE', key = { 1 }, to = 'пять', limit = 10 }).fields
-- { age = "должно быть целым числом не меньше 0, а не 'пять'" }
tnt_model_select('users', { index = 'age', iterator = 'EQ', key = { 999 }, limit = 10 }).fields
-- { age = 'должно быть целым числом от 0 до 150, а не 999' }
```

Выборка не по форме — неизвестный индекс либо итератор, ключ, курсор
или условия не таблицей, условие по полю не из формы либо со знаком,
которого нет, — ошибка вызывающего кода и исключение «модель users:
выборка не по форме: index, iterator, key, after, filter»: свои шлюзы
собирают выборку сами, и такую посылает только чужой код. Так же
исключение и граница `to` не у итератора `GE`: её ставит `between`,
выборка идёт от нижней границы вверх, и только так записи за верхней —
хвост выборки. У `EQ` и по убыванию разность счётов посчитала бы чужие
записи, поэтому узел такую выборку не исполняет — «модель users: граница
to — только у итератора GE, а не LT».

Способ удаления `tnt_model_delete`: пусто — по модели (мягко у модели
с признаком удаления, иначе окончательно), `force` — окончательно,
`restore` — восстановить; иной — отказ `invalid` «способ удаления purge
неизвестен». Мягкое удаление и восстановление отвечают записью, какой
она легла, окончательное — `true` либо `false`. Выборка `query` несёт
условия областей и мягкого удаления списком `filter` — `{ field, op,
value }`; поле из формы, знак и значение проверяются заново. Функции `tnt_model_*`
хуков не зовут, а отметки ставят: они пишут шлюзом `local`.

Права. В шардированном кластере роутер зовёт их через
`vshard.storage.call` под учёткой `iproto.advertise.sharding` — той, у
которой роль `sharding`; отдельных прав функциям не нужно. Узел-прослойка
и реплика с `writes: forward` зовут их напрямую под той же учёткой, и ей
нужны права на функции и на спейсы моделей: функцию, позванную
по `lua_call`, Tarantool исполняет с правами вызывающего, и без права
на спейс она отвечает «Read access to space 'users' is denied for user
'storage'». Права выдаются **у группы с данными**, а не глобально:
глобальное право на спейс, которого на прослойке нет, Tarantool держит
там предупреждением в `config:info().alerts` (статус `check_warnings`),
пока выдачу не уберут из конфигурации и узел её не перечитает, — тогда
статус снова `ready`, а `alerts` пуст. На узле с данными предупреждение
снимается само, как только миграция создаст спейс:

```yaml
credentials:
  users:
    storage: { password: '{{ context.storage_password }}' }
iproto:
  advertise:
    sharding: { login: storage }
groups:
  data:
    credentials:
      users:
        storage:
          password: '{{ context.storage_password }}'
          privileges:
            - permissions: [execute]
              lua_call: [tnt_model_find, tnt_model_put, tnt_model_delete, tnt_model_select, tnt_model_count]
            - permissions: [read, write]
              spaces: [users]
```

Учётка `iproto.advertise.sharding` — доверенная. С правом `write`
на спейс она пишет в него напрямую, мимо проверки модели: запись,
которую `tnt_model_put` отверг бы `invalid`, ложится как есть —
`box` сверяет её только с форматом спейса.

```lua
-- на прослойке, соединение с ведущим под учёткой storage
conn.space.users:replace({ 424242, '', 999, box.NULL })   -- легла: пустое имя, возраст за max
conn:call('tnt_model_put', { 'users', { id = 424243, name = '', age = 999 }, 'insert' }).kind   -- 'invalid'
```

Поэтому её пароль — ключ к данным моделей в обход формы, и держат его
как пароль к самим данным: узлу, которому данных не доверяют, его
не дают.

### Шлюз `sharded`

Бакет считается от ключа шардирования `vshard.router.bucket_id_mpcrc32`
— тем же хешем, что на хранилище (`vshard.hash.mpcrc32`), иначе запись
легла бы в чужой бакет; опознаватель — от строки (выше, «Опознаватели»).
`find`, `create`, `save`, `delete` и `where('id', '=', …)` идут в один
бакет (`callro`/`callrw`). Выборка по вторичному индексу и `scan` идут
на все репликасеты сразу (`map_callrw` — другого веера у vshard 0.1.42
нет, поэтому на ведущих), страницы сливаются в порядке индекса, `count`
складывается.

Отказ веера называет репликасет, на котором веер споткнулся: vshard
отдаёт его третьим значением `map_callrw` — «хранилище storage-002
не ответило: timed out». Отказ вызова в один бакет называет только
причину: хранилище там одно, и оно видно по ключу. После двоеточия —
ошибка vshard как есть, и причину молчания по ней не различить:
`timed out` бывает и у хранилища на паузе, чьё соединение живо, и у
живого, пока его бакеты переезжают (ниже, «Перенос бакетов»);
`Timeout exceeded` — и у погашенного, к которому соединение
не поднялось, и у живого, не выдавшего ссылку за срок.

#### Перечитывание конфигурации роутера

`config:reload()` на роутере заводит в vshard новые объекты
репликасетов, а прежние помечает устаревшими. Вызов в один бакет берёт
репликасет в миг отправки и перечитывания не замечает. Веер держит
объекты от ссылок до ответов, через уступки, и перечитывание, пришедшее
посреди, обрывает его ошибкой `OBJECT_IS_OUTDATED`, хотя хранилища
живы. Шлюз такой веер повторяет: `tnt_model_select` и `tnt_model_count`
только читают, а роутер к мигу отказа уже держит свежие объекты. Повтор
один и идёт в остаток того же срока: веер целиком не дольше `timeout`,
а второе перечитывание, закончившееся за время повтора, — отказ
`unavailable`. Перечитывание, заставшее веер в пути, — хранилище
на паузе держит ответ на ссылку, — обрывает голый `map_callrw`
ошибкой `OBJECT_IS_OUTDATED`, а веер модели повторяется и считает всё.
Двадцать перечитываний подряд, пока четыре файбера считают и читают
страницы веером, проходят без единого отказа.

Ссылки попытки, которую оборвало перечитывание, роутер уже не снимет:
отмену он шлёт через те же устаревшие объекты. Ссылки держатся
на хранилищах до конца срока веера, и перенос бакетов столько их ждёт.

#### Перенос бакетов

`map_callrw` берёт на каждом хранилище ссылку, которая держит бакеты
на месте, пока веер не ответит, поэтому ответ веера полон всегда:
неполного счёта и неполной страницы не бывает. Ссылка и перенос ждут
друг друга: пока хранилище отправляет или принимает бакеты, ссылку оно
не выдаёт, а перенос ждёт, пока выданные ссылки отпустят. Веер во время
переноса ждёт ссылку и, не дождавшись за срок, отказывает `unavailable`
с именем репликасета, чаще всего отправляющего, — «хранилище storage-001
не ответило: timed out», хотя хранилище живо. А поток вееров сам тормозит
перенос. Замер: два хранилища, 300 бакетов и 600 записей, десять бакетов
уезжают с одного на другое, нагрузка — четыре файбера на роутере:

| Нагрузка во время переноса | Перенос | Отказы |
|---|---|---|
| нет | 0,03 с | — |
| `find` | 0,08 с | 0 из 278 |
| `count` веером, срок 5 с | 30 с | 24 из 68 |

Вызов в один бакет переносу почти не мешает: он держит только свой
бакет, а бакет, уехавший посреди, vshard находит у нового хранилища
сам. Поэтому переносы — балансировку, добавление шарда — ведут, когда
веерных выборок мало.

Уникальный индекс `box` держит на каждом хранилище отдельно, поэтому
привязка на узле с ролью vshard пускает уникальный вторичный индекс,
только если среди его полей есть ключ шардирования (выше, «Объявить
модель»): записи с равными значениями такого индекса живут в одном
бакете, и хранилище этого бакета видит их все. Отказ `conflict` ставит
хранилище, и через роутер он приходит тем же текстом — с именем индекса.

#### Смещение через роутер

Хранилище не знает, сколько из пропущенных записей лежит у соседей.
Поэтому смещение веер хранилищам не передаёт: каждое отдаёт первые
`offset + limit` своих записей, роутер сливает их и отбрасывает первые
`offset`. **Страница номер N стоит N страниц записей с каждого
репликасета**: страница 500 по 20 записей в кластере из четырёх
репликасетов — это 4 × 10 000 записей, прочитанных, переданных по сети
и слитых роутером ради двадцати. Цена растёт с номером страницы, а не
с размером данных, и на глубокой странице роутер тратит на слияние
память и срез файбера. Выборка на равенство по ключу шардирования идёт
в один бакет, и там смещение уходит хранилищу как есть — все записи
ключа на одном узле.

Сумма `offset + limit` бывает больше 32 бит, хотя каждое слагаемое
годно, а её `box` молча обрезает. Поэтому хранилищам уходит не больше
`model.OFFSET` записей: дальше записи смещением через роутер не достать,
их листают курсором.

Глубину страниц держит список: номер страницы из адреса ограничивает
разбор запроса, а глубокие выборки листают курсором —
`after` стоит через роутер одну страницу с каждого репликасета на любой
глубине.

### Шлюз `remote`

Соединения открываются при первом обращении и закрываются
`binding.close()` при перечитывании конфигурации — без обрыва вызовов
в пути (ниже, «Перечитывание»). Ведущий заранее
не выбирается: запись пробует узлы репликасета по имени, узел с ответом
`readonly` пропускается, принявший запись запоминается и спрашивается
первым. Чтение идёт тем же порядком: к запомненному ведущему, а до
первой записи — к первому узлу по имени. Соединение, которое
не поднялось или оборвалось, при следующем обращении заменяется новым:
net.box без `reconnect_after` из состояния `error` не выходит, и узел,
вернувшийся после перезапуска, иначе молчал бы для шлюза
до перечитывания конфигурации.

Срок `timeout` — на узел: соединение и вызов укладываются в него
вместе, и соединение, поднявшееся к концу срока, оставляет вызову
остаток. Худший срок обращения — `timeout`, умноженный на число узлов:
столько ждёт вызов, когда молчат все. Три молчащих узла при умолчании
в 5 с — чтение отказывает через 15 с.

Узел, который промолчал, — соединение не поднялось, срок вышел, связь
оборвалась, — ведущим больше не считается и уходит в конец порядка,
пока снова не ответит. Зависший ведущий стоит срока один раз: следующие
чтения идут к соседу сразу, запись находит нового ведущего по отказам
`readonly`. Так же в конец уходит молчащая реплика, которая у свежей
привязки стоит первой по имени. Из опроса молчащий узел не выпадает:
его спрашивают последним, когда остальные промолчали или ответили
`readonly`, — и ответ, хотя бы ошибкой, возвращает его на место.
Молчавших несколько — первым из них идёт тот, кто замолчал раньше.

Отказ называет каждый узел и что с ним было:

| Узел | Текст |
|---|---|
| ответил `readonly` | «core-a: узел только для чтения: config» — после двоеточия текст узла (выше, «Отказы») |
| не ответил за срок | «core-a: нет ответа за 5 с» |
| связь не поднялась либо оборвалась | «core-a не отвечает: Peer closed» |
| ответил ошибкой | «core-a ответил ошибкой: Procedure 'tnt_model_put' is not defined» |
| получил запись и не ответил | «исход записи на core-a неизвестен: нет ответа за 5 с» |

Итог — по худшему: промолчал хоть один узел — «репликасет core
не ответил: …», ответил ошибкой — «репликасет core отказал: …», оба
`unavailable`: ведущим мог быть любой из них. Только если все ответили
`readonly` — «репликасет core не принимает запись: core-a: узел только
для чтения: config; core-b: узел только для чтения: config», род
`readonly`.

Запись исполняется не больше одного раза. К следующему узлу она идёт,
только когда на этом точно не легла:

- соединение не поднялось за срок `timeout` либо поднялось, когда срок
  уже вышел, — запрос не уходил: «core-a не отвечает: …», «core-a: нет
  ответа за 5 с»;
- узел ответил `readonly`;
- узел отверг вызов, не исполнив функцию: её ещё нет (`ER_NO_SUCH_PROC`),
  на неё нет права (`ER_ACCESS_DENIED`), узел только для чтения
  (`ER_READONLY`) — «core-a ответил ошибкой: …».

Вызов, который ушёл и не вернулся ответом, — вышел срок, связь
оборвалась после отправки, функция бросила исключение, — узел мог
исполнить. Такую запись шлюз дальше не несёт и сразу отвечает
`unavailable`, называя узлы, которые успел пройти: «репликасет core
не ответил: исход записи на core-a неизвестен: нет ответа за 5 с»;
исключение функции — ответ узла: «репликасет core отказал: исход записи
на core-a неизвестен: ответил ошибкой: …». Зависший ведущий (пауза
процесса, потеря сети) при `failover: election` исполняет запрос
из сокета, когда проснётся, и повтор у нового ведущего положил бы
запись второй раз. Оборвись соединение раньше, чем запрос дошёл, —
исход тоже сочтётся неизвестным: лишний отказ дешевле записи, легшей
дважды. Чтение данных не меняет и после любой ошибки идёт к следующему
узлу.

Перечитывание. `close` прежней привязки вызовов в пути не обрывает:
вызовов нет — соединения закрываются сразу, есть — шлюз помечается
закрытым и закрывает все свои соединения разом, когда вернётся
последний. Оборви он их сразу — запись, которую ведущий уже принял,
кончилась бы отказом «репликасет core не ответил: исход записи на core-a
неизвестен: Connection closed», а чтение ушло бы к соседу. До тех пор
вызов в пути идёт прежними правилами: запись, которой узел ответил
`readonly`, идёт к следующему узлу, а соединение с ним, если его ещё
не было, открывается — и закрывается вместе с прочими, не дожидаясь
сборки мусора. Так свежая привязка, ещё не знающая ведущего, переживает
и перечитывание, пришедшее следом: её первые записи ждут ответа первого
по имени узла, и откажи закрытый шлюз им в соединении с ведущим —
записи, которые тот принял бы, кончились бы отказом. Новых обращений закрытый шлюз
не принимает: модели к этому мигу смотрят на новую привязку, а тот, кто
держит прежний шлюз сам, сразу получает `unavailable` «репликасет core:
привязка закрыта» — без соединений. Отдельного срока у закрытия нет:
вызов кончается не позже худшего срока обращения, и столько же,
не дольше, живут соединения прежней привязки, — а обрыв по сроку
закрытия сделал бы запись, ушедшую второму узлу, записью с неизвестным
исходом. Под нагрузкой — двадцать файберов пишут через прослойку, десять
перечитываний, парами через миллисекунду, — отказов нет, и лишних
соединений на узлах с данными не остаётся.

### Пересылка записи с реплики

Реплика репликасета без шардирования по умолчанию отвечает на запись
`readonly`. С `writes: forward` она пересылает запись ведущему своего
репликасета — путём шлюза `remote`, и приложению на реплике не нужно
различать узлы:

```yaml
groups:
  data:
    roles: [app]
    roles_cfg:
      app:
        models: { writes: forward }
```

Учётка и права — те же, что у прослойки (выше): `iproto.advertise.sharding`
и у группы с данными `lua_call` на `tnt_model_*` и `read, write` на спейсы
моделей. Как это работает:

- запись сначала идёт на месте: ведущий — в том числе ставший им после
  смены — пишет у себя без перечитывания конфигурации. Только отказ
  `readonly` отправляет запись соседям по репликасету, себя в списке
  нет. Дальше как у прослойки: узел с `readonly` пропускается,
  принявший запоминается, отказ называет каждый узел — «репликасет core
  не ответил: core-a не отвечает: connect, …: Connection refused; core-c:
  узел только для чтения: config», `unavailable`. Запись, ушедшая
  к соседу без ответа, другому соседу не отдаётся: «репликасет core
  не ответил: исход записи на core-a неизвестен: нет ответа за 5 с»,
  `unavailable`; промолчавший сосед уходит в конец опроса, и следующая
  запись находит нового ведущего;
- чтение, `count` и `model.atomic` — на месте. Внутри транзакции запись
  не пересылается: вызов по сети уступает управление и обрывает
  транзакцию memtx, а пересланная запись легла бы мимо неё. Там отказ
  `readonly` с текстом «узел только для чтения: config; в транзакции
  запись ведущему не пересылается»;
- `conflict` и `invalid` ведущего доходят до вызывающего как есть; вход
  проверяется на реплике до пересылки и на ведущем заново;
- функции `tnt_model_*` реплики отвечают только своими данными
  и не пересылают: иначе две реплики с пересылкой гоняли бы запись друг
  другу до срока. Прослойке реплика отвечает `readonly`, как и прежде;
- `binding.status()` узла с `writes: forward` несёт `writes = 'forward'` —
  и у ведущего: раздел общий на группу, а кто ведущий, решает не он.

`writes: forward` — только у узла с данными без vshard. На узле с ролью
vshard запись ходит через роутер, у прослойки данных нет, а узлу без
соседей пересылать некому, — это исключения `model.bind`: «пересылка
записи: у узла с ролью vshard запись ходит через роутер», «пересылка
записи: у прослойки данных нет — шлюз remote и так пишет на ведущем»,
«пересылка записи: у узла solo-a нет соседей по репликасету solo».

### Шлюз `sql`

Источник `sql` кладёт данные модели в таблицу PostgreSQL либо MySQL.
Шлюз к базе пакет моделей не заводит и от баз SQL не зависит:
приложение собирает шлюз [`tnt-orm`](https://github.com/tnt-skein/tnt-orm)
над своим драйвером — `tnt-postgres` или `tnt-mysql` — и передаёт его
третьим аргументом `model.bind`:

```lua
local orm = require('tnt.orm')

local binding = model.bind({ User }, model.settings({ source = 'sql' }), { sql = orm.gateway(db) })
```

Шлюз — таблица с теми же полями, что у всякого шлюза модели: имя
`kind` (его отдаёт `Model.bound()`), действия `find`, `put`, `delete`,
`select`, `count`, `atomic`, `close` (ниже, «Проверки») и `migrate` —
схема таблицы по форме модели. Имя драйвера `driver` пакет моделей
проверяет и отдаёт в разделе из `model.settings`: по нему приложение
находит драйвер в своём контейнере. Функций `tnt_model_*` у такого узла
нет, а шаг `Model.migration()` создаёт таблицу в базе (ниже,
«Миграция»).
Та же модель работает и там — `find`, `create`, `save`, `delete`,
выборки, `after`, `offset`, отметки, хуки, мягкое удаление, области
и отказы теми же родами; чем таблица отличается от спейса
в транзакциях, типах и страницах, описывает документ шлюза
([`tnt-orm`](https://github.com/tnt-skein/tnt-orm/blob/main/docs/orm.md), «Чем SQL-шлюз отличается от спейсов»).

### Транзакции

`model.atomic(fn, …)` — `box.atomic` там, где данные: одиночный узел,
ведущий репликасета, хранилище, узел «и роутер, и хранилище» — по своим
бакетам. На шлюзе `sql` транзакцию ведёт сам шлюз — его `atomic`:
транзакция драйвера на одном соединении
([`tnt-orm`](https://github.com/tnt-skein/tnt-orm/blob/main/docs/orm.md), «Транзакции»).

Там, где данные в `box`, `model.atomic` не вкладывается — ни в себя,
ни в `box.atomic`: он открывает транзакцию `box`, а вторую внутри первой
ядро не открывает и бросает «Operation is not permitted when there is
an active transaction». Исключение, дошедшее до внешнего `model.atomic`
либо `box.atomic`, откатывает всю транзакцию — и записи, легшие до
вложенного вызова. Тело, которое зовут и из транзакции, и вне её,
спрашивает `box.is_in_txn()` и в транзакции зовётся без обёртки:

```lua
local ok, err = pcall(model.atomic, function()
    assert(User.create({ id = 8100, name = 'Внешняя', age = 30 }))

    return model.atomic(function() end)   -- вложенный вызов
end)

ok, err          -- false, 'Operation is not permitted when there is an active transaction '
User.find(8100)  -- nil: откат унёс и внешнюю запись
```

На выделенном роутере vshard и на прослойке транзакции нет, и это ошибка
программиста: `model.atomic` там бросает исключение, и запись модели
внутри транзакции `box` — тоже. Запись через роутер и прослойку уходит
по сети и ложится на узле с данными своей транзакцией: откат вызывающего
её не отменил бы, и транзакция молча вышла бы частичной. Чтение данных
не меняет и идёт как всегда.

```lua
local ok, err = pcall(box.atomic, function()
    assert(User.create({ id = 8101, name = 'Откат', age = 30 }))
    error('нарочный откат', 0)
end)

-- на выделенном роутере: create бросил, до хранилища запись не дошла
err        -- 'модель users: запись через роутер в транзакции невозможна — она ушла бы по сети и легла
           --  мимо транзакции; box.atomic живёт в функции хранилища, которую роутер зовёт callrw'
-- на прослойке: 'модель users: запись на узле без данных в транзакции невозможна — …'
-- на узле с данными и на узле «и роутер, и хранилище»: err — 'нарочный откат', запись ушла с откатом
User.find(8101)   -- nil везде
```

Тело транзакции живёт в функции узла с данными, которую роутер зовёт
`vshard.router.callrw` в пределах одного бакета. Функцию публикует
приложение на каждом узле с данными; права — те же, что у функций
`tnt_model_*` (выше, «Общие функции узла с данными»), а ответ — одна
таблица: vshard отдаёт вызывающему только первое значение.

```lua
-- на узлах с данными
rawset(_G, 'aged', function(id, age)
    return model.atomic(function()
        local user = assert(User.find(id))

        user.age = age

        return { age = assert(user:save()).age }
    end)
end)

-- на роутере
vshard.router.callrw(vshard.router.bucket_id_mpcrc32(7), 'aged', { 7, 44 })   -- { age = 44 }
```

Узел «и роутер, и хранилище» держит часть бакетов сам. Вне транзакции он
ходит через свой роутер, как выделенный, а внутри транзакции модель идёт
мимо роутера, к бакету ключа на месте, шлюзом `local`:

- `find`, `create`, `save`, удаление и восстановление, выборка в один
  бакет берут бакет ключа под ссылку vshard (`bucket_ref`) до конца
  транзакции; снимает её триггер фиксации либо отката. Раньше снимать
  нельзя: фиксация уступает управление на запись журнала, и перенос
  бакета, начатый в эту уступку, увёз бы его без записи;
- бакет ключа у другого репликасета — исключение «модель users: бакет 17
  не на этом узле — в транзакции узел «и роутер, и хранилище» читает
  и пишет только свои бакеты; транзакция над чужим живёт в функции его
  хранилища, которую роутер зовёт callrw», и откат уносит всё тело.
  Транзакция не выходит за свой репликасет, и тело, написанное для чужих
  данных, — ошибка программиста: отказ парой можно было бы не заметить
  и зафиксировать транзакцию без этой записи. Функция `aged` выше годится
  и здесь: на узле бакета модель пойдёт к нему на месте;
- бакет здесь, а ссылка не взялась — отказ парой с текстом vshard: узел
  не ведущий своего репликасета — `readonly`, бакет в переносе либо
  заперт — `unavailable`, «бакет 17: Bucket 17 is transferring to
  replicaset …»;
- выборка веером — `where` по вторичному индексу, `scan`, их `count` —
  исключение «модель users: выборка веером в транзакции невозможна — она
  шла бы через роутер по сети мимо транзакции; …»: вызов по сети уступил
  бы управление и оборвал транзакцию memtx, а чужих репликасетов она всё
  равно не охватывает.

```lua
-- на узле «и роутер, и хранилище», ключ 8102 — в его бакете
model.atomic(function()
    assert(User.create({ id = 8102, name = 'Вера', age = 30 }))

    local user = assert(User.find(8102))   -- видит запись, легшую в этой транзакции

    user.age = 31
    assert(user:save())

    return User.where('id', '=', 8102):count()   -- 1: выборка в один бакет
end)
```

## Миграция

`Model.migration()` — шаг `function(box)`: спейс с форматом
по объявлению, первичный индекс, индексы модели; на хранилище vshard —
ещё поле `bucket_id` на своём месте в списке полей и индекс по нему. Шаг
решает по узлу, где выполняется, а не по объявлению: одно объявление —
своя схема на каждой топологии. Допустимость пустого значения часть
индекса берёт из формата спейса (`is_nullable` у необязательного поля),
а не называет второй раз.

Модель, привязанная к шлюзу со своей схемой — шлюзу `sql`, — спейса
не заводит: шаг отдаёт форму шлюзу, и тот создаёт таблицу и индексы
в базе (`migrate` шлюза: `create table if not exists`,
[`tnt-orm`](https://github.com/tnt-skein/tnt-orm/blob/main/docs/orm.md), «Схема таблицы»).
Шлюз шаг смотрит в миг, когда идёт, а не когда его взяли, поэтому шаги
миграций приложения остаются теми же, когда источник меняется
настройкой. Отказ базы срывает шаг: версия схемы вперёд не уходит.

Три вещи, о которых надо знать заранее:

- **шаг над `box` выполняется один раз**: спейс он создаёт, не спрашивая,
  есть ли тот, и повтор на узле, где спейс уже есть, — исключение
  «Space 'users' already exists». Роль, которая зовёт шаг в каждом
  `apply`, упадёт на втором старте узла. Один раз шаг зовёт версия
  `tnt-schema`, а сценарий без неё — по проверке, что спейса ещё нет
  (выше, «Поднять схему»);
- **переезд между топологиями — отдельный шаг руками**: спейс без
  `bucket_id`, созданный на одиночном узле, при переводе узла в хранилище
  vshard сам поле не получит;
- **шаг создаёт спейс по нынешнему объявлению.** После первого выпуска
  правки формы — отдельными шагами: на новом узле первый шаг создаст
  спейс уже по новому объявлению, и следующие шаги обязаны это пережить
  (`if box.space.users:format()[5] == nil then … end`).

## Чем пришлось поступиться

- **Чтение с реплики и через `callro` может отставать** от ведущего:
  `find` сразу после `create` на другом узле вправе не увидеть запись.
  Это касается и реплики, переславшей запись: запись легла на ведущем
  и доезжает до неё журналом.
- **Пересылка записи с реплики включается разделом, а не сама**
  (`writes: forward`): ей нужна учётка `iproto.advertise.sharding`
  с правами на функции и спейсы моделей, которой у репликасета без
  прослойки может не быть, и она меняет смысл записи на реплике — запись
  уходит по сети. Без раздела реплика отвечает `readonly`, как раньше.
- **В транзакции реплика запись не пересылает**: тело `model.atomic`
  на реплике получает `readonly`. Транзакция над данными ведущего живёт
  в функции ведущего, как и через роутер.
- **Запись через роутер и прослойку внутри транзакции `box` — исключение,**
  а не запись по сети: легла бы она мимо транзакции, и откат её не отменил
  бы. Транзакция над данными — в функции узла с данными (`callrw`).
- **`model.atomic` не вкладывается.** Вторую транзакцию `box` внутри
  первой ядро не открывает: вложенный вызов — исключение, и, дойдя
  до внешней транзакции, оно откатывает её целиком. Тело, которое зовут
  и из транзакции, и вне её, спрашивает `box.is_in_txn()`.
- **Функции узла с данными переживают `close`.** У них свой шлюз
  `local`, и снимает их глобалы тот, кто публиковал, — при остановке
  роли; иначе роутер и прослойка пишут в спейс узла и после неё.
- **Узел «и роутер, и хранилище» в транзакции видит только свои бакеты.**
  Чужой бакет и веер там — исключение, и тело над чужими данными живёт
  в функции их узла. Вне транзакции такой узел ходит через свой роутер —
  по сети даже к своим бакетам.
- **`unavailable` при пересылке и у прослойки не значит, что записи
  нет**: ведущий мог её принять, а ответ — не дойти за срок. Шлюз такую
  запись не повторяет; повтор вызывающего получит `conflict`, только
  если первая запись уже лежит там, куда он придёт: у того же живого
  ведущего либо у нового, куда она доехала журналом. Промолчавший узел
  уходит в конец опроса, и повтор через тот же шлюз идёт уже к новому
  ведущему: пока прежний висит, повтор `create` проходит, а прежний,
  проснувшись, исполняет первую — запись ложится дважды.
- **Зависший ведущий при `failover: election` разводит репликасет и без
  пакета.** Запрос, который ждёт в его сокете, он исполнит, когда
  проснётся, — в прежнем сроке, и соседи остановят репликацию от него:
  «Split-Brain discovered: got an async transaction from an old term».
  Так ведёт себя асинхронная репликация Tarantool при выборах; пакет
  лишь не добавляет второго исполнения. Срок шлюз платит один раз:
  запись, ушедшая к зависшему ведущему, ждёт срок и отвечает
  `unavailable`, а сам узел уходит в конец опроса — следующие чтения
  идут к соседу сразу, записи — к новому ведущему.
- **Веер по репликасетам идёт на ведущих и под ссылками**:
  `map_callrw` — единственный веер у vshard 0.1.42. Ссылка держит
  бакеты на месте до ответа, поэтому во время переноса бакетов веер
  ждёт её, может отказать по сроку и сам замедляет перенос — в замере
  десять бакетов уезжали 30 с вместо 0,03 с (выше, «Шлюз `sharded`»).
- **Веер, застигнутый перечитыванием конфигурации роутера, повторяется
  один раз** и в остаток своего срока: второе перечитывание за время
  повтора — отказ `unavailable`. Ссылки оборванной попытки роутер
  не снимет, и перенос бакетов ждёт их до конца срока веера.
- **Отказ веера называет репликасет, но не причину**: текст vshard после
  имени одинаков у погашенного хранилища, у зависшего и у живого, чьи
  бакеты переезжают.
- **Смещение через роутер стоит `offset + limit` записей с каждого
  репликасета.** Передать смещение хранилищам нельзя: сколько пропущенных
  записей у соседей, никто из них не знает. Номер страницы ограничивают,
  глубоко листают курсором.
- **Смещение и страница — до 2^32 − 1.** Дальше `box` их обрезает,
  и модель отвечает исключением, а не чужой страницей. Через роутер
  дальше записи номер 2^32 − 1 смещением не достать: хранилищам уходит
  не больше стольких записей, глубже листают курсором.
- **Ключ шардирования — часть первичного ключа**, иначе `find` через
  роутер потребовал бы обхода всех хранилищ.
- **Уникальность по кластеру — только с ключом шардирования в индексе.**
  `box` сверяет уникальный индекс в своём спейсе, то есть внутри
  репликасета, и вторичный индекс без ключа шардирования уникальность
  по кластеру не держит: такую модель привязка на узле с ролью vshard
  не пускает. Логин, уникальный во всём кластере, держат отдельной
  моделью, где сам логин — ключ шардирования; запись в неё и в основную
  модель через роутер — два бакета и не одна транзакция, и легшую
  половину при отказе второй снимает вызывающий.
- **`select` по ключу на равенство идёт в один бакет только когда ключ
  шардирования — первое звено первичного ключа**; иначе веером.
- **Целое от 10^14 в записи — cdata, а не число Lua**, как его отдаёт
  `box`: `math.max` его не берёт, а ключ таблицы Lua ищет по cdata,
  а не по значению. Ключ больше 2^53 передают cdata
  (`9007199254740993ULL`): число Lua `2^53 + 1` уже равно `2^53`,
  и модель этого не заметит.
- **Шаг схемы из объявления сам не применяется**: он регистрируется
  шагом миграции через `Model.migration()`. Порядок версий принадлежит
  приложению, а не алфавиту имён моделей: модель и миграция живут
  порознь нарочно — одна описывает форму, другая знает, в каком порядке
  схема к ней пришла.
- **Прослойка объявляет себя сама.** `source: auto` никогда не даёт
  `remote`: без vshard узел с данными и узел без данных по ролям
  неотличимы, и прослойка без `models: { source: remote, replicaset: … }`
  получит шлюз `local`, схему у себя и пустые спейсы.
- **Права на спейсы моделей — у группы с данными.** `credentials`
  глобального уровня выдают право на спейс и на прослойке, где спейса
  нет, — Tarantool держит это предупреждением, пока выдачу не уберут
  из конфигурации и узел её не перечитает.
- **Учётка шардирования пишет мимо проверки модели.** Функции
  `tnt_model_*` исполняются с правами вызывающего, и учётке
  `iproto.advertise.sharding` нужны `read, write` на спейсы моделей,
  а с ними она пишет в спейс и напрямую. Узел с данными не верит
  вызывающему функции, но учётке он верит: она доверенная, как и сам
  роутер.
- **Одно приложение с моделями на процесс.** Привязка одна на процесс,
  и `attach` следующей переключает `model.atomic` на себя, а функции
  узла с данными зовутся `tnt_model_*` у любого приложения: второе
  в том же процессе заняло бы те же имена.
- **Выборка с условием читает больше, чем отдаёт.** Области и мягкое
  удаление `box` не знает, и узел с данными берёт записи индекса
  кусками, проверяя каждую: страница из двадцати записей, под которую
  подходит каждая тысячная, читает двадцать тысяч. Смещение с условием
  читает пропущенные записи — индекс их больше не перескакивает, —
  а через роутер каждое хранилище отдаёт `offset + limit` подошедших.
  Частое условие делают индексом и ищут по нему `where`. **Вне
  транзакции** обход длиннее куска уступает между кусками и узел
  не держит, но это не снимок: за уступкой соседи дописывают и стирают,
  и прочитанное складывается из кусков, снятых каждый в свой миг.
  **Внутри транзакции** уступать нельзя — уступка обрывает транзакцию
  memtx («Transaction has been aborted by a fiber yield»), — и там обход
  идёт без уступок и срывается исключением «fiber slice is exceeded»,
  когда исчерпает срез файбера: разбор и сверка записи стоят около
  4 мкс (замер на 3.8: 200 000 записей — 0,8 с), и срез по умолчанию —
  секунду — длинная выборка исчерпывает на четверти миллиона записей.
  Длинную выборку с условием делают вне транзакции.
- **`count` у модели с мягким удалением — обход.** Условие «не удалена»
  стоит на каждой выборке, и `index:count` его не знает: счёт идёт
  кусками по всей выборке, как счёт с областью. Вне транзакции обход
  уступает между кусками и узел не держит, но это чтение каждой
  записи, а не счёт по индексу; `with_deleted():count()` без областей
  считает по индексу, как прежде, и диапазон `between` — тоже.
  В транзакции обход с условием идёт без уступок и упирается в срез
  файбера — предел назван выше, у выборки с условием.
- **Удалённая запись занимает ключ и уникальные индексы.** `create`
  с ключом мягко удалённой записи — `conflict`, и уникальный вторичный
  индекс не даст второй записи то же значение, пока первая не стёрта
  `force_delete`.
- **Хуки идут у вызывающего.** Функции `tnt_model_*` их не зовут, поэтому
  вызов по `lua_call` мимо модели хуки обходит. Отметки же ставит узел
  с данными, и их не обойти.
- **Хук «после» не отменяет записи.** Вне транзакции запись уже легла;
  внутри `model.atomic` его исключение откатывает транзакцию.
- **`original` хука изменения — запись, какой её прочитали,** а не
  свежая из хранилища: между чтением и `save` соседи вправе её поменять.
  Хуку, который сторожит состояние, читать свежее самому — на узле
  с данными в `model.atomic`.
- **Удаление по ключу у модели с хуками — чтение и удаление.** Хуку нужна
  запись; чтение идёт тем же путём, что `find`, — через роутер `callro`,
  на прослойке к запомненному ведущему либо первому узлу по имени —
  и вправе отставать: запись, которую чтение ещё не видит, удаляется
  с ответом `false`, без хуков.
- **`save` записи, которую не читали, — создание для хуков.** Замена
  по ключу при этом остаётся заменой: запись с тем же ключом уйдёт,
  а отметку создания и признак удаления узел возьмёт у неё.
- **Отметки — стенные часы узла с данными.** Хранилища с расходящимися
  часами ставят отметки, несравнимые точно, а перевод часов назад даёт
  `updated_at` раньше `created_at`. Длительность по отметкам не меряют.

## Проверки

Проверки лежат в `test/` и идут на luatest; зовутся они через `make`,
который держит каталог узлов luatest своим.
Модель без узла проверяется двойником шлюза (`User._bind(gateway)`), где
шлюз — таблица с `find`, `put`, `delete`, `select`, `count`, `atomic`,
`close` и, у шлюза со своей схемой, `migrate`, а внешние средства
подменяются как внешние зависимости:

```lua
local model = require('tnt.model')

model._set_source({
    router = function() return fake_router end,     -- vshard.router: bucket_id_mpcrc32, callro, callrw, map_callrw
    hash = function() return fake_hash end,         -- vshard.hash: mpcrc32 — бакет записи на хранилище
    config = function() return fake_config end,     -- get, info, instances, instance_uri
    net_box = function() return fake_net_box end,   -- connect
    storage = function() return fake_storage end,   -- vshard.storage: bucket_ref, bucket_unref — ссылка на бакет в транзакции
    box = function() return fake_box end,           -- space, is_in_txn, on_commit, on_rollback, error, info, atomic
    fiber = function() return fake_fiber end,       -- yield: уступка в долгом обходе
    clock = function() return fake_clock end,       -- realtime: час отметок времени
})
```

Подменяется только названное, остальное берётся настоящим. Бакет
считают двое: шлюз `sharded` — роутером (`bucket_id_mpcrc32`), шлюз
`local` на хранилище vshard — сам, хешем `mpcrc32`, и сверяет его
с `_bucket` узла. Проверка хранилища без `hash` поэтому грузит настоящий
`vshard.hash`; двойник даёт бакет, какой нужен проверке.

Шлюз `local` проверяется и так — на двойнике `box`: подменённый индекс
показывает, какими счётами идёт счёт по диапазону, какими кусками —
выборка с условием и сколько раз шлюз уступил (`test/local_test.lua`),
а на живом узле то же место проверено под срезом файбера. Отметки
времени на живом узле сверяются точным значением: час подменяет внешняя
зависимость `clock` (`test/features_live_test.lua`), и одна проверка
идёт с настоящими часами `tnt-clock`.

Живые проверки (`*_live_test.lua`) поднимают настоящие узлы Tarantool
в дочерних процессах и ставят vshard 0.1.42 из `.rocks`: одиночный узел,
репликасет из трёх процессов, прослойка перед репликасетом, репликасет
с выборами, где ведущего останавливают сигналом SIGSTOP, роутер с двумя
хранилищами, узел с обеими ролями vshard и два таких узла в двух
репликасетах. Оснастка — `test/helper.lua`:
`helper.users(model)` — модель пользователей, `helper.fake_gateway(answers)`,
`helper.fake_net_box(nodes, calls, clock)` — двойник net.box для шлюза
`remote` (вызов к узлу с каналом `gate` ждёт, пока проверка его
не отпустит, — так вызов остаётся в пути), `helper.fake_clock(lag)` —
двойник часов, по которым шлюз `remote` считает срок узла, а шлюз
`sharded` — остаток срока для повтора веера, `helper.timed_out()` — ошибка, которой net.box
кончает вызов по сроку, `helper.start_box()` — узел с настоящим `box`
и исходниками пакета, `helper.start_stand(config, ports, names,
options)` — несколько процессов под одной конфигурацией кластера, `helper.core_config(ports, leader,
members, rest)` — её текст для репликасета core с учётками стенда
(без ведущего — с выборами), `helper.free_port()` — порт под узел,
`helper.connections(servers, names)` — соединения iproto на узлах,
`helper.write_under_reloads(server, base)` — двадцать писателей, пока
узел десять раз перечитывает конфигурацию, `helper.publish_aged(servers,
names)` — функция `aged` из «Транзакций» на узлах с данными,
`helper.await_replication(servers, names)` — ожидание, пока репликация
стенда встанет, `helper.pages_by_email(server, base)` — обход индекса
почты страницами по 1, 3 и 7 на узле стенда и
`helper.assert_pages_by_email(seen, base)` — его сверка с выборкой
целиком.
Останавливают их `helper.stop_node` и `helper.stop_stand`. Сценарий узла
стенда `test/node.lua` делает руками то, что приложение делает при
применении конфигурации: раздел `models` из меток узла (срок — меткой
`model_timeout`), `model.settings`, `model.bind`, `attach`, функции узла
с данными глобалами, миграция там, где узел принимает запись; глобал
`rebind` — перечитывание: новая привязка по тому же разделу и `close`
прежней; модели сверх стендовых проверка передаёт ему списком — так
проверки уникального индекса и опознавателей через роутер привязывают
свои модели мест и устройств на всех узлах и потом отпускают. Моделей
на стенде две: пользователи с необязательной почтой в индексе и записи
блога с отметками, мягким удалением и областью — по ним видно, что курсор
с пустой почтой, способ удаления и условия выборки доходят до хранилища
через роутер.

Покрытие строк — 100 %, убитых мутантов — 100 % (255 проверок, из них
58 живых в семи наборах; 1959 строк в двадцати двух модулях).
